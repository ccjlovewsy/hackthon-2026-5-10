StackMap 是什么，为什么 Kotlin/Native 的 GC 需要它

接着 01-kotlin-native编译全链路 把镜头推近一格：编译器把 .kt 翻成 LLVM IR 之后， GC 凭什么知道"栈上哪个槽位装着活对象引用"——答案就是 StackMap。

0GC 扫栈这道题

GC 标记阶段要找"活对象"，起点叫根集合（root set），包括三类：

图 1 · GC 扫根集合的三类起点，栈是其中最难的一类

栈是一段连续内存，里面混着返回地址、保存的寄存器、本地变量、临时值……GC 怎么知道 sp + 0x28 这个位置现在是 Int 还是某个 ObjHeader*？

两条路：① 朴素办法——把栈整段当指针扫（conservative GC），缺点是会把不是对象的东西误当对象，永远不敢回收。 ② Kotlin/Native 选了精确栈图（precise stackmap）——编译期就把"每个 GC 安全点上，哪些栈槽/寄存器装着对象引用"全发出来，GC 照图扫。

1两种找栈根的办法

由编译开关 ENABLE_STACKMAP 决定走哪条路。

模式 名字 怎么做 开关
OFF 影子栈
shadow stack		 编译器在每次可能触发 GC 的调用前后，把活引用手动 push/pop 到一个旁路栈 ENABLE_STACKMAP 未定义
ON 精确栈图
precise stackmap		 编译器发 LLVM stackmap 元数据；GC 走真实 fp 链，按 PC 查表 ENABLE_STACKMAP=1
权衡：影子栈慢（每次调用多两条指令）但简单；精确栈图零运行期开销，但编译期和 runtime 都要会读一份"地图"。

OHOS 分支 ohos_arm64 和 macos_arm64 默认走 ON（runtime/build.gradle.kts:73）：

runtime/build.gradle.kts:73默认 ON
if (resolveEnableStackmap(project, target)) {
    compilerArgs.add("-DENABLE_STACKMAP=1")
    compilerArgs.add("-DENABLE_COMPRESSED_BITMAP_STACKMAP=" +
        if (resolveEnableCompressedStackmap(project, target)) "1" else "0")
}

2一份 stackmap 长什么样

LLVM 把所有 GC 安全点的元数据塞进一个特殊段，符号叫 _LLVM_StackMaps（macOS）或 __LLVM_StackMaps（Linux/OHOS）。

图 2 · .llvm_stackmaps 段布局：一串定长记录

每条 StkMapRecord（即一个安全点）里，核心是 numLocations 个 Location：

runtime/src/gc/common/cpp/StackMap.hppLocation 结构
struct Location {
    enum class Kind: uint8_t {
        REGISTER = 1, DIRECT = 2, INDIRECT = 3,
        CONSTANT = 4, CONSTANTINDEX = 5,
    };
    Kind location;
    uint16_t locationSize;
    uint16_t dwarfRegNum;       // DWARF 寄存器号(如 fp=29, sp=31)
    int32_t  offsetOrSmallConstant;
};
读法举例：INDIRECT + dwarfRegNum=29 + offset=0x28 的意思就是： "此刻 fp + 0x28 这个栈槽装着一个对象引用"。GC 扫栈时把每条 INDIRECT Location 的 offset 加到对应帧的 fp 上，读出来的就是根指针。

3帧怎么找到"自己的"那份 stackmap

一个 .kexe 里几千个函数、几万个安全点，GC 拿着一个帧的 PC 怎么定位到对应的 Location？

黑历史：压缩位图模式（ON）曾踩过坑。debug 构建会把多个模块的 .llvm_stackmaps 拼到一起， 每个模块的索引是模块局部的，模块 M 的帧去查模块 0 的 offsets 表 → 错位。

修法很巧——让每个帧自带"我属于哪个 stackmap blob"的指针。函数 prologue（ARM64 上对 ADRP 指令的一次 hijack）在进函数时执行：

函数 prologue · ADRP hijackO(1) 查找
ADRP x?, .Lstackmap_start.<func>   // PC-relative, link 期解析
ADD  x?, x?, #lo12:.Lstackmap_start.<func>
STR  x?, [fp, #-16]                // 存进 *(fp - 2)
STR  funcStartPC, [fp, #-8]        // 存进 *(fp - 1)

GC 拿到 fp 就能直接 *(fp - 2) 取到该帧的 stackmap blob 地址，高 16 位是 tag（掩码去掉），低 48 位是真实地址。

ConcurrentMark.cpp:161 · GetStackMapAddress查找入口
static uint64_t *GetStackMapAddress(uint64_t *fp, uint32_t *funcStartPC, mm::ThreadData& thread) {
    // The function prologue (AArch64AsmPrinter ADRP hijack) now stores the
    // absolute address of .Lstackmap_start.<func> directly into *(fp - 2) ...
    // (the per-module/per-blob index + offsets-table indirection used
    // previously was broken under multi-blob debug builds: indices were
    // per-module-local, so module M>0 frames indexed module 0's offsets).
    uint64_t addr = *(fp - 2);
    constexpr uint64_t payloadMask = (1ULL << 48) - 1;
    return reinterpret_cast<uint64_t*>(addr & payloadMask);
}
这个设计点很值钱：stackmap 的查找是 O(1) per frame，不依赖任何全局表，天然支持多模块 link。 压缩位图模式敢用 lazy per-function 查找，前提就是这帧能直接找到自己的 blob。

4GC 扫一次栈的完整流程

入口：runtime/src/gc/cms/cpp/ConcurrentMark.cpp:230 的 tryCollectRootSet。

图 3 · tryCollectRootSet 完整流程：从抢锁到入队根对象
ConcurrentMark.cpp:230 · tryCollectRootSetCMC GC 标记阶段入口
void gc::mark::ConcurrentMark::tryCollectRootSet(mm::ThreadData& thread, MarkTraits::MarkQueue& markQueue) {
    auto& gcData = thread.gc().impl().mark_;
    if (!gcData.tryLockRootSet()) return;          // ① 抢这个线程的 root set 锁
    gcData.publish();                               // ② 先发布 TLS pending roots
    collectRootSetForThread<MarkTraits>(...);       // ③ 走 baseline(TLS / 全局 / shadow-stack)
#ifdef ENABLE_STACKMAP
    std::vector<FrameInfo> frameInfos = GetStackFrame(thread);   // ④ fp 链 unwind
    if (frameInfos.empty()) return;
    for (size_t i = 0; i < frameInfos.size(); i++) {
        if (frameInfos[i].fa == 0 || frameInfos[i].ip == 0) continue;
        uint64_t* fp = reinterpret_cast<uint64_t*>(frameInfos[i].fa);
        const uint32_t* pc = reinterpret_cast<const uint32_t*>(frameInfos[i].ip);
        std::vector<int32_t> baseRoots;
        CollectStackMapBaseRoot(thread, fp, pc, baseRoots);      // ⑤ 查这帧的 stackmap
        for (auto& baseRootOffset : baseRoots) {
            uintptr_t address = (uintptr_t)fp + baseRootOffset; // ⑥ fp + offset = 根槽地址
            ObjHeader* object = (ObjHeader*)*((uint64_t*)address);
            if (!object) continue;                              // ⑦ 跳过 null
            KNStateWord *word = reinterpret_cast<KNStateWord*>(object);
            if (!(word->IsValid())) continue;                   // ⑧ 跳过半构造对象
            internal::collectRoot<MarkTraits>(markQueue, object); // ⑨ 入队
        }
    }
#endif
}

⑤ CollectStackMapBaseRoot（ConcurrentMark.cpp:180）在压缩位图模式下用 StackMapBuilder::collectHeapReferenceMap 把这帧所有"装堆引用的栈槽相对 fp 的偏移"提取出来：

ConcurrentMark.cpp:180 · CollectStackMapBaseRoot查这帧的 stackmap
uint32_t *funcStartPC = reinterpret_cast<uint32_t*>(*(fp - 1));
uint64_t *stackMapAddress = GetStackMapAddress(fp, funcStartPC, thread);
stackmap::StackMapBuilder stackMapBuilder(
    reinterpret_cast<uintptr_t>(funcStartPC),
    reinterpret_cast<uintptr_t>(pc),
    stackMapAddress);
stackMapBuilder.collectHeapReferenceMap(base2DerivedOffsets);

④ GetStackFrame 在 runtime/src/mm/cpp/FpUnwind.cpp 里，沿着 fp 链一帧一帧往上走，识别帧类型（KOTLIN_FRAME / K2N_STUB / RUNTIME_FRAME 等，见 FpUnwind.h:69 的 FrameType 枚举），只对 KOTLIN_FRAME 帧做 stackmap 查找——因为只有 Kotlin 编译器发的代码才有 stackmap，runtime/stub 的帧不归 GC 管。

5valid 位：分配器和 GC 之间的握手协议

⑦ 跳过 null 好懂。⑧ KNStateWord::IsValid() 才是关键。

runtime/src/main/cpp/TypeInfo.h:100握手位
// Precise-stackmap object valid-state word. Bit 59 of typeInfoOrMeta_ is
// set on object construction (CustomAllocator::CreateObject/CreateArray)
// and read by GC sweep (ConcurrentMark) to skip half-constructed objects.
constexpr unsigned kValidBitNoHwasan = 59;
constexpr unsigned kValidBitHwasan   = 2;

class KNStateWord {
public:
    ALWAYS_INLINE static uint64_t ValidBit() noexcept {
        return uint64_t{1} << (kotlin::compiler::isHwasanEnabled() ? kValidBitHwasan : kValidBitNoHwasan);
    }
    void SetValid()      { state_ |= ValidBit(); }
    bool IsValid()       { return (state_ & ValidBit()) != 0; }
private:
    uint64_t state_;
};

KNStateWord 是 ObjHeader::typeInfoOrMeta_ 字段的别名视图（同一块 64 位内存换个类型读）。bit 59 是"这个对象头已经写完，GC 可以扫"的标志位。

为什么需要？分配一个对象不是原子的。如果栈上某个槽已指向这块新内存（val x = Foo() 编译成"先分配、再存到 x 的栈槽"），但 typeInfoOrMeta_ 还没写完或刚写完 valid 位还没置，GC 这时扫过来读 typeInfoOrMeta_ 就是垃圾值 → 解引用 TypeInfo → 崩。

valid 位就是分配器和 GC 之间的"我这边写完了，你可以读"信号。

分配器侧两个入口都必须置位：

  • CustomAllocator::CreateObject / CreateArray（custom 分配器，CustomAllocator.cpp:62/87）
  • ObjectFactory::CreateObject / CreateArray（std/legacy 分配器，ObjectFactory.hpp:548）
典型 bug：后者（std/legacy 分配器）是 OHOS 分支 05b4e469a77（主题 1-3）补上的——原代码只在 custom 分配器置位， 结果用 std/legacy 分配器构造的对象 valid 位恒为 0，栈根引用它们时被 GC 当半构造对象跳过 → 漏扫 → UAF。 这是个非常典型的"两个分配器镜像同一段逻辑，漏掉一个就出 bug"的故事。
runtime/src/alloc/custom/cpp/CustomAllocator.cpp:37置位流程
object->typeInfoOrMeta_ = clearPointerBits(typeInfo, OBJECT_TAG_MASK);  // 写 typeInfo
// ... 中间可能被 GC 中断 ...
#ifdef ENABLE_STACKMAP
    KNStateWord *word = reinterpret_cast<KNStateWord*>(object);
    word->SetValid();                                                    // 置 valid 位
#endif

6为什么是 bit 59，HWASan 下又挪到 bit 2

TypeInfo.h:92 那段注释值得单独讲。

图 4 · bit 59 vs bit 2：HWASan 用了高 8 位做 pointer tag，valid 位只能挪到对象头对齐空隙
  • 非 HWASan：bit 59。typeInfoOrMeta_ 高 16 位（bits 48-63）是 tag 位，正常对象指针（48 位地址）不会用到，放个标志位安全。
  • HWASan：hardware-assisted sanitizer 用 bits 56-63 做 pointer tag，bit 59 被吃了 → 挪到 bit 2（对象头对齐空隙，因为 ObjHeader 起始 8 字节对齐，低 3 位本来是 0）。
  • kotlin::compiler::isHwasanEnabled() 是 app 侧在链接期发出的常量全局变量，linker 能把 ValidBit() 里的三目运算折叠成一条常量。零运行期开销。
"not a bitfield: bitfield offsets are fixed at compile time"——这是在解释为什么用 1 << n 而不是 C bitfield： bitfield 偏移是编译期固定的，做不到这种"运行期读全局常量选位"的折叠。一个很容易被忽略的工程细节。

7ON/OFF 不是开关那么简单：同一份 runtime 服务两种 app

这是这套机制里最绕的一点，FpUnwind.h:19 的注释专门写了。

图 5 · 同一份 runtime .bc 服务两种 app：靠 weak 引用 + 不可达路径

ENABLE_STACKMAP 是 runtime 的编译期开关（决定 runtime 的 .bc 怎么编），但同一份 runtime .bc 会被链进两种 app：

  • ON app：KonanConfig.enableStackmap=true，编译器发 stackmap + 链 asm stub .o
  • OFF app：KonanConfig.enableStackmap=false，不发 stackmap + linker 丢掉 asm stub .o

runtime .bc 是 ON 编译的，所以 FpUnwind.cpp 的实现体故意不 #ifdef 掉——它在 OFF runtime 里也得能编译。但 FpUnwind.cpp 里读的那些 stub PC 锚点被声明为 weak：

FpUnwind.h:60-64 · weak 引用关键设计
extern uintptr_t unwindPCForN2KStub __attribute__((weak));
extern uintptr_t unwindPCForKonanStartStub __attribute__((weak));
// ...

这样 OFF app link 时把 stub .o 丢了，这些 weak 引用解析为 0 → Is*Stub() 永不匹配 → 精确栈走逻辑不可达，行为等同于"ON 链了但永不被执行的 stub 代码"。好处是不用维护两套 runtime 变体。

本质：这是典型的"用一个不可达路径换一份二进制"的取舍。 要理解为什么 ON 的 runtime 能安全链进 OFF app，得先理解：OFF app 不发 stackmap，所以 GC 根本不会走 tryCollectRootSet 里那个 #ifdef ENABLE_STACKMAP 块——它走的是 baseline shadow-stack 路径，weak 引用 0 不 0 都无所谓。

一句话：你看不懂 stackmap，就看不懂 GC 为什么会扫到坏指针；看不懂坏指针，调查 CMC GC 崩溃就只能靠猜。 这也是为什么 problem-map 把"主题 1 → 主题 5"列在前面的学习顺序里。

9小结

  • StackMap = 编译期发的"此刻哪些栈槽/寄存器是活引用"元数据，落在 .llvm_stackmaps 段，每个 GC 安全点一条 record。
  • GC 标记阶段靠它走真实 fp 链扫栈（tryCollectRootSet → GetStackFrame → CollectStackMapBaseRoot），而不是影子栈。
  • ON/OFF 是 per-target 编译开关；同一份 ON runtime 能安全链进 OFF app，靠的是 weak 引用 + 不可达路径。
  • valid 位（bit 59，HWASan 下 bit 2）是分配器和 GC 之间的握手：对象头没写完置位前，GC 跳过它。
  • 这条链上长过 UAF、TOCTOU SIGSEGV、no-op 漏扫——都是 GC 调查的高频坑。
下一篇建议：《Safepoint：mutator 怎么知道该停下来等 GC》——因为 stackmap 是贴在 safepoint 上的（每个 safepoint 一条 record），没有 safepoint 也就没有 stackmap。 而 tryCollectRootSet 之所以能安全读 mutator 的栈，前提是 mutator 此刻正停在某个 safepoint 上。这两件事是一体的两面。
