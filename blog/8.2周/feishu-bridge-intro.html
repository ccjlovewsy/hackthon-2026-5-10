1这是什么

一句话定位 + 一张架构图。

核心定位：飞书机器人 = opencode CLI 的远程入口。在飞书聊天框发指令 → 桥调本机 opencode serve → 敏感操作先发审批 → 用户回复"允许/拒绝" → 结果回传飞书。

2核心能力

桥提供的 6 大能力。

💬

飞书指挥 opencode

飞书聊天框发指令，桥调 opencode serve 执行，结果回传。多轮上下文连续。

🔐

人工审批

敏感操作（写文件、跑命令）先发审批消息，回复 允许/拒绝/总是允许 才放行。

📤

进度推送端点

任意本机程序 POST /progress 推消息到飞书，无需飞书凭证。

🔄

launchd 常驻

开机自启、崩溃 10s 内自动拉起。关掉所有终端仍在跑。

👥

白名单授权

只有 OPENCODE_ALLOWED_USERS 里的飞书账号能指挥，陌生人被拒。

⏱️

超时保护

OPENCODE_TIMEOUT_MS 兜底，默认 45 分钟，防止任务卡死。

3双通道架构

桥同时维护两条通道，方向和用途不同。

通道 方向 需要凭证 用途
主通道
飞书聊天 → 桥 → opencode serve		 双向
（飞书指挥 + 结果回传）		 桥持有飞书 App Secret 主交互通道：发指令、收审批、看结果
进度通道
POST /progress		 单向
（本机 → 飞书）		 无需凭证 任意本地程序往飞书推消息（如编译完成通知）
关键设计：进度通道复用桥已认证的飞书 SDK 身份发消息，调用方不需要任何飞书凭证—— 任何能发 HTTP 请求的程序（curl / opencode 会话 / shell 脚本）都能往飞书推消息。
最简调用 · 一行 curl无需凭证
curl -X POST http://127.0.0.1:41235/progress \
  -H "content-type: application/json" \
  -d '{"text":"阶段1 编译完成，kexe 1.6M，ELF aarch64 校验通过"}'
安全：/progress 端点只绑 127.0.0.1，不对外网暴露，本机任何进程都能调。 如需限制，用 macOS 防火墙挡 41235，或在源码加 token 校验。

+hello
回复「允许」继续，「拒绝」中止，「总是允许」本次会话后自动放行
三种回复语义：
  • 允许 → 该次操作继续执行
  • 拒绝 → 中止该操作
  • 总是允许 → 同范围后续自动放行（会记住，整会话有效）

5launchd 常驻与崩溃自愈

桥作为用户级 LaunchAgent 运行，开机自启 + 崩溃即拉。

图 2 · launchd 父子关系：launchd (PID 1) 直接托管桥，桥 spawn 出 serve。崩溃自动拉起。
launchd 字段 实测值 含义
type LaunchAgent 用户级 agent，登录后启动，注销后停止
state running 当前在跑
keepalive true 进程退出立即重新 spawn（崩溃自愈的关键）
runatload true 开机/登录自动启动
jetsam memory limit unlimited 不被系统内存压力杀
exit timeout 5 秒 SIGTERM 后等 5s 不退就 SIGKILL
关键限制：launchd 能拉起进程但恢复不了会话状态。 桥崩溃后新桥复用旧 serve，但旧 serve 里卡住的 write 会话还在，新桥不感知 → 用户看到的现象是"桥活了，但旧指令没继续"。这才是要修的根因。

6资源占用

空闲稳态实测（2026-08-10），近理论最低。

进程 CPU 内存 说明
feishuBot.mjs（桥） 0.0% ~54 MB 挂在飞书 WebSocket 长连接，事件驱动，无轮询
opencode serve 0.0~1.3% ~360 MB HTTP 监听 127.0.0.1:41234，无请求时 idle
launchd 本身 0% 0 只是配置 + 进程表项，KeepAlive 是内核事件通知，不轮询
结论：空闲功耗已近理论最低，无需再加守护/降功耗进程——任何 watchdog 自己也要运行和唤醒，属于负优化。 macOS 的 App Nap 还会自动压制无活动后台进程。
不建议为省 360MB 改为"用时再启动 serve"：opencode 冷启动需加载 36+ 插件， 首条指令可能挂几分钟（见进度文档"踩过的坑"第 2 条），会破坏随时聊天的体验。 常驻保温是合理取舍。

7使用流程

从配对到日常使用的完整步骤。

首次配对：在飞书找到机器人发一条消息，机器人回复身份 id（ou_xxx / uu_xxx / on_xxx）。
填白名单：把 ou_ 开头的 id 填入 .env 的 OPENCODE_ALLOWED_USERS，重启桥。
发指令：飞书聊天框发指令，如"用 write 工具创建文件 /tmp/test.txt，内容 hello"。
审批：opencode 需要写文件时，机器人发审批消息，回复 允许 / 拒绝 / 总是允许。
看结果：执行完成后，opencode 的结果回传飞书。同一会话上下文连续（多轮协作）。
成功标志：能收到审批消息并放行 = 整条链路通了。
  • 未授权用户发消息会被拒绝（白名单外）
  • opencode 执行过程日志实时写入 data/opencode-logs/（可 tail -f）
  • 回复超 4000 字符会截断并标注，属预期

9排错速查

常见现象 + 处理。

启动报「缺少 FEISHU_APP_ID / FEISHU_APP_SECRET」
.env 没填或没保存
启动后看不到「长连接已启动」、全是 [error] [ws] connect failed
App ID/Secret 错误，或应用未发布
发消息没任何反应（日志也无事件）
① 应用未发布 ② 事件没添加 im.message.receive_v1 ③ 订阅方式不是长连接 ④ 这个应用被 OpenClaw 等其它进程占用（换新应用）
机器人回「🚫 未授权」
正常首次行为，按配对流程把 ou_ id 填进 OPENCODE_ALLOWED_USERS 重启
机器人回「❌ opencode 出错」
opencode 执行失败，回复里带 exit code 和 stderr；检查 OPENCODE_DIR 是否存在、opencode 是否有权限访问
指令发出后没有收到 🔐 审批消息
该操作不在 ask 规则内（被 allow/deny）；或权限请求挂起中但 SSE 断了（桥日志看 [opencode-serve] SSE 断开，3s 自动重连）
回复了「允许」但没反应
审批请求可能已过期（会话被 abort）；查看桥日志的 权限回复失败，或重发指令
机器人回「⏱️ 执行超时」
任务跑太久（默认 45 分钟兜底），或权限一直没人批导致挂起；检查是否有未处理的 🔐 审批消息
回复被截断
回复超 4000 字符会截断并标注，属预期

10安全须知

三条红线。

红线 1 · 白名单是唯一防线：能私聊机器人 = 能指挥本机 opencode 执行代码。 只放行你信任的账号。
红线 2 · App Secret 等同于本机执行权限：别泄露、别提交到 git（.env 已被忽略）。
红线 3 · 别和 OpenClaw 复用应用：同一应用多个长连接会随机抢事件，导致两边都收不全消息。 必须新建应用。
