1一句话症状

这是整个 bug 最关键的一句，所有现象都从它展开。

libcrt 的 STW GC 路径（ark_collector.cpp 的 EnumRootsImpl<VisitGlobalRoots>）只调 VisitGlobalRoots， 而它被上游改成了 no-op → STW 时 Kotlin globals + stable refs 全部丢失 → 上述 3 个用例从 0 fails 变 3 fails。

3根因：分叉语义漂移（契约不匹配）

这不是手抖写错，是两个分叉对"谁负责扫 root"的理解发生了漂移。

    const RefFieldVisitor& visitor)

    // no-op —— 上游假设
    // 没人再走这条路

 * → 函数空 → root 集合空

修复后 · bd0abd533c9 FIX 
// KNRootVisitor.cpp:352
void KNRootsVisitor::VisitGlobalRoots(
    const RefFieldVisitor& visitor)
{
    // NOTE: move concurrent roots out
    // of global roots later.
    for (auto& thread : GlobalData::Instance()
            .threadRegistry().LockForIter()) {
        thread.Publish();  // ① 先发布
    }
    VisitConcurrentRoots(visitor); // ② 再委托
}
关键变化：VisitGlobalRoots 不再 no-op，而是 STW 路径 = publish + 并发路径，让 STW 和并发两条路覆盖同一份 root 集合，契约重新对齐。

① GlobalRootsStress

在测什么
8 worker × 1000 轮，每轮验证 4 个全局 globalStress1..4 + StressGlobalHolder.p1/p2/p3，然后 GC.collect()
为什么 FAIL
GC 看不见 7 个全局 root → 它们被回收 → worker 读到被破坏对象 → verify() 返回 false
关键：7 个全局对象只能通过 global root 被 GC 找到。GC 没扫到 root → 对象被回收 → verify() 失败。

② StableRefStress

testsuite/stability/gc-concurrent/StableRefStress/StableRefStress.kt
在测什么
1000 个 StableRef，8 worker 并发 refs[i].get().verify()，另一线程狂调 GC.collect()
为什么 FAIL
StableRef 在 Kotlin 侧靠 SpecialRefRegistry 注册，注册项也走 global root 发布 → STW 看不见 → 指向对象被搬/回收 → get() 返回悬垂引用
StableRef 注册项作为 global root 发布，STW 路径丢 root → 指向对象可能被搬动后旧指针失效，或被回收。

6修复思路：让 STW 和并发覆盖同一份 root

核心动作：VisitGlobalRoots 不再 no-op，改成 publish + 委托并发路径。

遍历 threadRegistry，对每个线程调 Publish() —— 把各线程 TLS 里 pending 的 global/special root 发布到公共集合。
委托 VisitConcurrentRoots(visitor) —— 走并发路径扫公共集合。
效果：STW 路径和并发路径覆盖同一份 root 集合，契约重新对齐。
