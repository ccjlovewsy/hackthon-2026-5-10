# 飞书桥崩溃排查 —— 2026-08-11

> 接续文档：`docs/opencode-飞书人工审批桥接方案-进度.md`
> 现象：飞书 × opencode 桥进程两次退出，launchd 自动拉起，但卡住的写文件操作无法恢复。

## 一、现象

- **崩溃时间**：2026-08-10 深夜 ~2026-08-11 11:08 PM（两次间隔约数小时，均由 launchd KeepAlive 拉起）
- **错误日志**（`data/opencode-logs/feishu-bot.launchd.err.log`）：

- **进程态**：launchd 1 秒内拉起，新桥 `src/backend/app/feishuBot.mjs` (PID 52099) + 新 `opencode serve` (PID 52101) 正常监听 41234。但旧会话 `ses_0162328d...` 的挂起 `write` 已无法恢复，目标文件 `docs/2026-08-10-今日工作总结.md` 最终未落盘。

## 二、根因

### 主因：fetch 异常未捕获 → 整进程退出

`feishuBotCore.mjs` 里多处 `fetch` 调用缺顶层 try/catch，特别是 `createSession` / `sendMessage` / `replyPermission` 这三处：

```js
// feishuBotCore.mjs:243-263 createSession
async function createSession() {
  const r = await fetch(`${base}/session`, { ... });   // ← 1) fetch 本身可能抛
  const j = await r.json();                            // ← 2) 读 body 也可能抛
  if (!r.ok || !j.id) throw new Error(...);
  ...
  const chk = await fetch(`${base}/session/${j.id}`);  // ← 3) 轮询又抛
  ...
}

// feishuBotCore.mjs:266-298 sendMessage：POST 后每 1s 轮询 GET message
const r = await fetch(`${base}/session/${sessionID}/message`, { ... });
if (!r.ok) throw new Error(...);
const j = await r.json();                              // ← 同上
```

链路里任意一次 `fetch` 抛错（HeadersTimeout / ECONNRESET / serve 重启），都沿 `handleMessage → queued → sendMessage` 一路冒到 `lark.EventDispatcher` 注册的回调，飞书 SDK 虽然在回调外有 try/catch（日志第一段 "事件处理失败"），但**同一 rejection 还会触发 Node 的 `unhandledRejection`**（日志第二段 `triggerUncaughtException`），Node 24 默认 `--unhandled-rejections=throw`，直接 `process.exit(1)`。

> 关键点：错误信息出现两次（先 "事件处理失败" 后 "triggerUncaughtException"），说明 SDK 吞了一次但 Node 全局钩子又抓到同一 Promise，第二次没兜住 → 进程退出。

### 诱因：serve 长流式输出导致 HTTP 响应头超时

`sendMessage` 走 HTTP 轮询（每秒 GET `/session/{id}/message`，等 `step-finish` part）。当 opencode 正在生成超长回复（主日志可见数百条 `message.part.delta`），serve 的 HTTP 响应可能迟迟不返回响应头，触发 undici 默认的 `headersTimeout`（Node 24 下约 300s）→ 抛 `UND_ERR_HEADERS_TIMEOUT`。

SSE 长连接 `/event` 与轮询并发打同一个 serve，长流式输出期间资源紧张会放大这个超时。

### 次要 bug：审批回复带标点识别不出来

`parseApprovalReply` 用 `single[t]` 精确匹配，对带标点的回复返回 `null`：

| 用户回复 | 解析结果 |
| --- | --- |
| `允许` | `{reply:"once"}` ✅ |
| `允许，` | `null` ❌ |
| `允许,` | `null` ❌ |
| `允许。` | `null` ❌ |

`null` 表示"不是审批回复"，于是走"新指令"路由。主日志第 742/744/746 行可见：用户回复「允许，」→ 桥当作**新指令**发给 opencode 执行 → 触发新的 `write` → 新的 `permission.asked`（`per_fec21c4d...`）→ 转飞书 🔐 → 桥随后崩溃 → 写文件未完成。

这是用户感知"发了允许但没写文件"的直接原因之一。

## 三、触发链路（时间线）

```
用户指令「把今天的总结写到 docs/2026-08-10-今日工作总结.md」
  → 桥调 sendMessage（POST message）
  → opencode 发起 write 工具 → permission.asked per_fec21c4d...
  → 桥转飞书 🔐 审批消息
  → 用户回复「允许，」
  → parseApprovalReply 返回 null → 走新指令路由
  → 桥把「允许，」当新指令发给 opencode
  → opencode 再次发起 write → 又一个 permission.asked
  → 桥转飞书 🔐
  → 桥进程 fetch 超时 → 未捕获 rejection → Node 退出
  → launchd 拉起新桥 + 新 serve
  → 旧会话 ses_0162328d... 的挂起 write 永远停在那里
  → docs/2026-08-10-今日工作总结.md 不存在
```

## 四、修复建议

### P0 — fetch 全部包 try/catch（防进程退出）

`feishuBotCore.mjs` 的 `createSession` / `sendMessage` / `replyPermission` 三处，把 `await fetch` + `await r.json()` 整段包进 try/catch，`sendMessage` 的轮询循环里 catch 后继续下一轮（已有内层 catch 但范围不够，没盖住 `r.json()` 和 POST 那次）。

入口 `feishuBot.mjs` 的 `handleMessage` 回调外再加一层兜底 `process.on("unhandledRejection", ...)` + `process.on("uncaughtException", ...)`，只记日志不退出（让 launchd 不必反复拉起）。

### P0 — 拉长 / 关闭 undici headersTimeout

`fetch` 改用带自定义 `dispatcher` 的 undici Agent：

```js
import { Agent } from "undici";
const agent = new Agent({ headersTimeout: 0, bodyTimeout: 0 });
fetch(url, { dispatcher: agent, ... });
```

`headersTimeout: 0` 关掉超时（serve 是本地 127.0.0.1，不会真挂）；`bodyTimeout: 0` 同理。轮询本来就有自己的 deadline，不依赖 undici 的 HTTP 层超时。

### P1 — parseApprovalReply 容错

匹配前 `trim` + 剥掉尾部中英文标点：

```js
const t = String(text ?? "").trim().toLowerCase().replace(/[，,。.!！?？]+$/, "");
```

这样 `允许，` / `允许.` / `允许！` 都能识别。已写单测 `tests/feishuBot.test.mjs`，加几条标点用例。

### P1 — 会话卡住后的自愈

`sendMessage` 检测到会话长时间无 `step-finish` 且无 pending permission 时，主动判定会话僵死，清掉 `sessionMap[chatId]` 让下次开新会话（避免复用卡住的旧会话）。当前需要手动删 `data/feishu-sessions.json`。

### P2 — 崩溃可观测

- `data/opencode-logs/` 加崩溃计数与最近一次崩溃原因文件（`crash.last.txt`），方便飞书机器人启动时主动播报"上次崩于 X，原因 Y"。
- launchd plist 已有 KeepAlive，建议加 `ThrottleInterval=10` 防止雪崩重启。

## 五、验证

- 复现：手动 `kill -STOP` serve 进程模拟超时，触发 `sendMessage` 轮询 fetch 抛 HeadersTimeout → 期望修复后只记日志不退出。
- 回归：`npm test`（`tests/feishuBot.test.mjs` 9 项 + 新增标点用例）全过。
- 真实链路：飞书发「允许，」「允许.」「允许！」→ 期望都能正确放行，不再被当新指令。
