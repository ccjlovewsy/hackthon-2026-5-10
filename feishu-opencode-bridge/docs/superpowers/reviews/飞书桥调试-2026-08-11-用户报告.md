# 飞书桥调试记录 —— 2026-08-11(用户报告)

> 用户报告两个问题:
> 1. 进入会话时连续收到两条"✅ 桥已连接..."欢迎消息
> 2. 发消息后 opencode 不回消息

## 一、问题 1:进入会话连发两条欢迎消息

### 现象

用户进入与机器人的单聊会话时,连续收到两条相同的"✅ 桥已连接"消息。

### 代码定位

`src/feishuBot.mjs:125-129`:

```js
"im.chat.access_event.bot_p2p_chat_entered_v1": async (data) => {
  const chatId = data?.chat_id;
  if (!chatId) return;
  await sendToFeishu(chatId, "嗨 👋 我在呢...");
},
```

handler 只注册一次,`sendToFeishu` 也只调一次,代码层面不会发两条。

### 可能根因

#### 假设 A:飞书平台重推事件(最可能)

飞书长连接在弱网/连接抖动时,可能对 `access_event` 类事件也重推。我们的 `isDuplicateMessage` 去重逻辑(`feishuBotCore.mjs:497`)只对 `im.message.receive_v1` 的 `message_id` 生效,**不覆盖 `access_event` 类事件**(这类事件没有 `message_id`,只有 `event_id`)。

证据:日志 `feishu-bot.log` 中确实多次出现 `忽略重复消息: om_x100b68993...`,说明飞书长连接确实在重推 `message.receive` 事件。`access_event` 很可能在同一时间窗口内也被重推。

#### 假设 B:用户触发了多次"进入会话"

飞书"用户进入机器人会话"事件的触发时机包括:
- 首次打开机器人会话
- 删除会话后重新搜索打开
- 飞书客户端切换导致的会话状态重置

若用户在短时间内多次进出会话(或客户端重连),会触发多次事件。

#### 假设 C:启动期间 launchd 拉起 + 旧实例未完全退出

`launchd KeepAlive` 在拉起新桥时,旧实例可能还在处理事件,导致两条 `sendToFeishu` 并发执行。

### 修复建议

**P0 — 给 `access_event` 加去重**

`feishuBotCore.mjs` 抽一个通用的 `isDuplicateEvent(eventId)` 纯函数(或复用 `isDuplicateMessage`,改成接受任意 id),在 `feishuBot.mjs:126` 加:

```js
"im.chat.access_event.bot_p2p_chat_entered_v1": async (data) => {
  const chatId = data?.chat_id;
  if (!chatId) return;
  // 假设事件体里有 event_id 或 chat_id + timestamp 组合
  const eventId = data?.event_id ?? `enter:${chatId}:${data?.event_time ?? ""}`;
  if (isDuplicateEvent(eventId)) return;
  await sendToFeishu(chatId, "嗨 👋 我在呢...");
},
```

需要查飞书文档确认 `bot_p2p_chat_entered_v1` 事件体里是否有 `event_id` / `event_time` 字段。

**P1 — 限流(更稳妥)**

per chatId 限流,3 秒内只发一次欢迎消息:

```js
const welcomeSentAt = new Map(); // chatId → timestamp
"im.chat.access_event.bot_p2p_chat_entered_v1": async (data) => {
  const chatId = data?.chat_id;
  if (!chatId) return;
  const now = Date.now();
  const last = welcomeSentAt.get(chatId) ?? 0;
  if (now - last < 30_000) return;  // 30 秒内已发过,不重发
  welcomeSentAt.set(chatId, now);
  await sendToFeishu(chatId, "嗨 👋 我在呢...");
},
```

这是更通用的方案,不依赖事件体字段。

## 二、问题 2:用户发消息,opencode 不回消息

### 现象

用户发消息,机器人无回复。

### 代码定位 + 日志证据

日志里有大量这种循环:

```
2026-08-11T08:02:17.553Z [INFO] [feishuBotCore] 指令 chat=oc_9591...: "[无辜笑]"
2026-08-11T08:02:20.442Z [INFO] [feishuBotCore] 执行 (session ses_01049a942...): "[无辜笑]"
2026-08-11T08:02:43.292Z [ERROR] [feishuBot] 事件处理失败 :: This operation was aborted
2026-08-11T08:02:51.179Z [INFO] [feishuBotCore] 忽略重复消息: om_x100b68993ec1d4a...
2026-08-11T08:02:55.190Z [INFO] [feishuBotCore] 指令 chat=oc_9591...: "你是否能识别表情"
2026-08-11T08:02:55.756Z [INFO] [feishuBotCore] 执行 (session ses_01049a942...): "你是否能识别表情"
2026-08-11T08:03:11.419Z [ERROR] [feishuBot] 事件处理失败 :: This operation was aborted
2026-08-11T08:03:33.935Z [INFO] [feishuBotCore] 忽略重复消息: om_x100b68993c698cb...
```

### 根因分析

**核心问题:`This operation was aborted` 错误说明 `fetchWithRetry` 的 `AbortController` 在超时后 abort 了 fetch。**

错误链路:

1. 用户发消息 → `handleMessage` → `queued(chatId, ...)` → `server.sendMessage(sessionID, text)`
2. `sendMessage`(`feishuBotCore.mjs:266+`)调 `fetchWithRetry` POST 指令 + 轮询 GET 结果
3. `fetchWithRetry` 设了 `timeoutMs: 5000, retries: 1`(`feishuBotCore.mjs:274`)
4. opencode serve 处理指令期间,5 秒内没返回响应头 → `AbortController` abort → 抛 `This operation was aborted`
5. 重试一次,仍超时 → 错误冒到 `handleMessage` 的 catch(`feishuBot.mjs:121`)
6. 全局错误处理器吞掉,但**没有给用户回复错误消息**

#### 为什么 opencode 5 秒不返回?

opencode 处理指令(LLM 调用 + 工具执行)通常需要 10-60 秒,5 秒超时太短。

#### 为什么用户感觉"不回消息"?

看 `handleMessage` 路由 2(`feishuBotCore.mjs:583-638`):

```js
return queued(chatId, async () => {
  // ...
  try {
    try {
      outText = await server.sendMessage(sessionID, text);  // ← 这里超时抛错
    } catch (err) {
      if (!isSessionNotFound(err)) throw err;  // ← 非 404 错误直接重抛
      // ...
    }
  } catch (err) {
    sessionLog?.append(chatId, `ERROR: ${formatErr(err)}`);
    metrics.messagesFailed++;
    throw err;  // ← 重抛到 feishuBot.mjs:118 的 try/catch
  }
  // ... reply(chatId, finalText) 永远到不了
});
```

错误重抛后,`feishuBot.mjs:117-122` 的 catch 只记录日志,**没有给用户发错误回复**:

```js
"im.message.receive_v1": async (data) => {
  try {
    await core.handleMessage(data);  // ← 抛错
  } catch (err) {
    // 兜底:单条事件失败不影响后续事件与长连接
    logger.error("feishuBot", "事件处理失败", err);  // ← 只记日志,用户看不到
  }
},
```

**用户感知**:消息发了,桥日志有 ERROR,但飞书里什么都没收到 → "不回消息"。

#### 副作用:重复消息风暴

飞书在桥没回复后自动重推消息(`忽略重复消息` 日志可见),但去重只挡住重复执行,不会触发回复——用户依然看不到任何反馈。

### 修复建议

**P0 — POST 指令的超时调大**

`feishuBotCore.mjs:274` 的 POST `/message` 超时 5 秒太短,opencode 处理指令通常 10-60 秒。改为 30 秒(POST 只是把指令塞进队列,不应该花 5 秒,但保险起见调大):

```js
const r = await fetchWithRetry(`${base}/session/${sessionID}/message`, {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ parts: [{ type: "text", text }] }),
  timeoutMs: 30_000,  // ← 从 5000 改为 30000
  retries: 1,
});
```

**P0 — 错误时给用户回复**

`feishuBot.mjs:117-122` 的 catch 里,补一条错误回复:

```js
"im.message.receive_v1": async (data) => {
  try {
    await core.handleMessage(data);
  } catch (err) {
    logger.error("feishuBot", "事件处理失败", err);
    // 给用户回复错误,避免"发了消息没反应"
    const chatId = data?.message?.chat_id;
    if (chatId) {
      await sendToFeishu(chatId, `❌ 处理失败:${err?.message ?? err}\n可发 /kill 重置会话后重试。`).catch(() => {});
    }
  }
},
```

**P1 — 轮询超时也调大**

`sendMessage` 轮询 GET `/message` 的 `fetchWithRetry` 也是 `timeoutMs: 5000, retries: 1`,但轮询本身就有 deadline(默认 45min),单次轮询 5 秒超时其实合理(超了重试即可)。不过 `retries: 1` 在持续无响应时会让错误冒上来——考虑把轮询的 `retries` 调到 3 或更高,让 fetchWithRetry 更有韧性。

**P2 — 验证 opencode serve 响应时间**

`curl -X POST http://127.0.0.1:41234/session/<sid>/message -d '{"parts":[{"type":"text","text":"hi"}]}'` 计时,确认 POST 响应头到达时间。如果 > 5 秒,那 5 秒超时就是直接根因。
