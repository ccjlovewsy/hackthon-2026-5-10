# Markdown → 飞书知识库：API 转换上传方案

> 目标：本地用 Markdown 写文档,通过飞书开放平台 API 转换为 docx block 结构,上传到指定知识库节点。
> 基础：复用本仓 `feishu-opencode-bridge` 已持有的飞书自建应用(`FEISHU_APP_ID`/`FEISHU_APP_SECRET`)和 `@larksuiteoapi/node-sdk` 依赖,无需新建应用。
> 预计耗时：首次接入约 30~60 分钟(权限审批 + 最小路径验证;转换优先用官方接口,无需自写解析器)。
> 修订：2026-10-23 审查后修正调用链与多处事实错误,见文末「审查记录」。

---

## 一、方案总览

```
本地 .md 文件
   │
   ├─► Markdown → Block 转换
   │     (优先官方接口:POST /docx/v1/documents/blocks/convert
   │      自写 remark 转换器兜底,处理官方输出需清洗/不支持的部分)
   │     └─► 飞书 docx Block 数组 (page / text / heading1-9 / bullet / ordered
   │           / code / quote / divider / table / image)
   │
   ├─► 创建知识库节点 (wiki/v2/spaces/{space_id}/nodes, node_type=origin)
   │     └─► 返回 node_token + obj_token(即 document_id,文档从诞生就在知识库)
   │
   ├─► 批量插入子 block (docx/v1/documents/{id}/blocks/{block_id}/children)
   │     (表格等嵌套结构走 descendant 创建嵌套块接口)
   │
   ├─► 图片三步:创建空 image block → upload_all(parent_node=image_block_id)
   │     → PATCH replace_image 绑定 file_token
   │
   └─► 返回 https://<租户>.feishu.cn/wiki/<node_token>
```

> ⚠️ **关键差异**:飞书 docx 的 block 模型与 Markdown 不是 1:1。常见陷阱:
> - 嵌套列表飞书用 `parent_id` 树状结构,Markdown 用缩进
> - 代码块语言字段飞书是枚举,Markdown 是任意字符串(需做映射或丢弃)
> - 表格单元格在飞书里是独立 block;且表格**不能用普通 children 接口创建**(报 1770029),必须走 descendant 嵌套块接口
> - 图片不能直接嵌 URL(外链图片会失联);上传素材的 `parent_node` 是**图片 block 的 block_id** 而非 document_id——必须先建空 image block,再传素材,最后 PATCH 绑定
> - 官方 convert 接口输出的 block 需清洗:剥 `style`、重映射 `block_id`、表格块去掉 `cells` 字段、叶子块补 `children: []`

## 二、前置准备

### 1. 飞书应用权限补充

`feishu-opencode-bridge` 现有应用权限只开了 `im:message` 系列。上传知识库需补开以下权限(应用详情 → 权限管理 → 搜索开通 → 重新发布版本):

| 权限 | 用途 |
| --- | --- |
| `docx:document` | 创建、读取、编辑 docx 文档 |
| `docx:document:readonly` | 只读(可选,排查问题时用) |
| `wiki:wiki` | 知识库节点增删改查、加入文档 |
| `wiki:wiki:readonly` | 知识库只读(找 space_id 时用) |
| `drive:drive` | 上传图片素材、文件管理 |
| `drive:file:upload` | `upload_all` / `upload_prepare` 接口前置 |

### 2. 把应用加进目标知识库(容易卡住的一步)

仅有 API 权限不够,应用对目标知识库还需有成员/管理员身份,否则 wiki 接口报 403。机器人账号常无法直接加为知识库成员,通行做法(群组授权法):

1. 建一个飞书群,把机器人拉进群
2. 知识库设置 → 成员管理 → 把该**群组**加为管理员
3. 机器人通过群组身份获得空间内节点的创建/编辑权

### 3. 找到目标知识库参数

先导出凭证并拿 tenant_access_token(自建应用):

```bash
set -a; source .env; set +a   # 导出 FEISHU_APP_ID / FEISHU_APP_SECRET

TOKEN=$(curl -s -X POST "https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal" \
  -H "Content-Type: application/json" \
  -d "{\"app_id\":\"$FEISHU_APP_ID\",\"app_secret\":\"$FEISHU_APP_SECRET\"}" | jq -r .tenant_access_token)

# 列出当前应用可见的知识库空间 → 拿 space_id
curl -X GET "https://open.feishu.cn/open-apis/wiki/v2/spaces?page_size=50" \
  -H "Authorization: Bearer ${TOKEN}"
```

拿到 `space_id` 后,需要知道挂载位置的 `parent_node_token`(根节点留空表示挂到空间根)。可用 `GET /wiki/v2/spaces/{space_id}/nodes` 列节点树。

### 4. 把这两个值写进 `.env`

```bash
FEISHU_WIKI_SPACE_ID=xxxxxxxxxxxx
FEISHU_WIKI_PARENT_NODE_TOKEN=   # 留空=挂到知识库根节点
```

## 三、核心 API 调用链

### 1. 获取 tenant_access_token

复用 `@larksuiteoapi/node-sdk` 自动管理,无需手动刷 token:

```js
import lark from "@larksuiteoapi/node-sdk";

const client = new lark.Client({
  appId: process.env.FEISHU_APP_ID,
  appSecret: process.env.FEISHU_APP_SECRET,
  appType: lark.AppType.SelfBuild,
  // SDK 自动在后台维护 token,无需手动 fetch
});
```

### 2. 创建知识库节点(文档随节点一并创建)

```
POST /open-apis/wiki/v2/spaces/{space_id}/nodes
Body: {
  "obj_type": "docx",
  "parent_node_token": "<可选,空=空间根>",
  "node_type": "origin",
  "title": "<文档标题>"
}
```

`node_type=origin` 会**新建**一篇空 docx,返回 `node.node_token` 和 `node.obj_token`(即 document_id)。文档从诞生就在知识库里,无需 folder_token、无需移动。

> ⚠️ 该接口**不接受已有文档的 obj_token**。若要把一篇已存在的云文档迁入知识库,改用 `POST /wiki/v2/spaces/{space_id}/nodes/move_docs_to_wiki`。

### 3. 批量插入 block(核心)

```
POST /open-apis/docx/v1/documents/{document_id}/blocks/{block_id}/children
Body: { "children": [...blocks], "index": 0 }
```

- `block_id` = 文档根 block 的 id(`document_id` 即根)
- `children` = 转换后的 block 数组
- 单次最多 50 个 block,超出需分批(同一接口 index 递增)
- ⚠️ **表格等含子结构的 block 不能用本接口创建**(报 1770029),需走创建嵌套块接口一次写入整棵块树:

```
POST /open-apis/docx/v1/documents/{document_id}/blocks/{block_id}/descendant
Body: { "children_id": [...], "descendants": [...] }
```

### 4. 图片三步流程(顺序不能反)

```
① 先创建空 image block(children/descendant 接口),拿到 image_block_id
② POST /open-apis/drive/v1/medias/upload_all
   multipart: file_name=xxx.png, parent_type=docx_image,
              parent_node=<image_block_id>,   # 是 block_id,不是 document_id!
              size=<字节数>, file=<二进制>
③ PATCH /open-apis/docx/v1/documents/{document_id}/blocks/{image_block_id}
   Query:  document_revision_id=-1            # -1 表示最新版本
   Body:   { "replace_image": { "token": "<file_token>" } }
```

飞书的设计是素材必须挂在图片 block 下:先有块,再传素材,最后绑定。与直觉的"先上传再引用"相反。

### 5. 更新已有文档(增量同步用)

```
① GET /docx/v1/documents/{document_id}/blocks/{document_id}/children   # 列出根下所有 block
② POST /docx/v1/documents/{document_id}/blocks/{document_id}/children/batch_delete
   Body: { "start_index": 0, "end_index": <children 数量> }             # 清空正文
③ 按第 3、4 步重新插入
```

## 四、Markdown → Block 转换

> **优先用官方转换接口**(2025-08 上线):`POST /docx/v1/documents/blocks/convert`,
> 直接把 Markdown/HTML 字符串转成 block 数组,省掉自写解析器。注意:
> - 输出需清洗:剥 `style`、重映射 `block_id`、表格块去掉 `cells` 字段、叶子块补 `children: []`
> - 有社区反馈内容顺序偶发错乱,插入后应抽查校验
> - 图片仍需走第三节第 4 步的三步流程,convert 不会代传素材
>
> 下表的自写映射作为官方接口覆盖不到/输出不符合预期时的兜底。

| Markdown AST 节点 | 飞书 docx block type | 备注 |
| --- | --- | --- |
| `heading` (depth=1) | `block_type: 3` (headings 1-9 对应 3-11) | depth 限制 1-9 |
| `paragraph` | `block_type: 2` (text) | children 是 text_run 数组 |
| `bulletList` | 每项 `block_type: 12` (bullet) | 嵌套用 `parent_id` |
| `orderedList` | 每项 `block_type: 13` (ordered) | 同上 |
| `taskListItem` (`- [ ]`) | `block_type: 17` (todo) | 原生支持,`style.done` 表示勾选 |
| `code` | `block_type: 14` (code) | `style.language` 是枚举,未知语言用 `plain` |
| `blockquote` | `block_type: 34` (quote container) | 引用容器,内部再装子 block |
| `thematicBreak` | `block_type: 22` (divider) | — |
| `table` | `block_type: 31` (table) + 子 cell blocks | 必须走 descendant 接口创建 |
| `image` | `block_type: 27` (image) | 三步流程,见第三节 |
| `link` (行内) | `text_run.text_element.style.link` | URL 写进 `link.unseal_value` |
| `strong` / `em` | `text_run.text_element.style` 的 `bold` / `italic` | — |
| `inlineCode` | `text_element.style.inline_code` | — |
| HTML 标签 | ❌ 不支持 | 需先转 markdown 或丢弃 |

### 不支持的 Markdown 特性(需降级)

- HTML 块 / 行内 HTML → 丢弃或转纯文本
- 脚注 / 定义列表 → 转 paragraph
- 数学公式 → 飞书有 equation block,但语法是 LaTeX 子集,需测试
- Mermaid / 流程图代码块 → 保留为 code block 或预渲染成图片上传

## 五、落地实现

### 方案 A:基于现有桥加新模块(推荐)

在 `feishu-opencode-bridge/src/` 下新增:

```
src/
├── mdToWiki.mjs           # 入口:CLI 主流程(convert → 清洗 → 建节点 → 插 block → 插图)
├── mdToBlocks.mjs         # 自写转换器兜底 + convert 输出清洗(纯函数,可单测)
└── feishuWikiClient.mjs   # 飞书 docx/wiki API 封装
```

CLI 用法:

```bash
node src/mdToWiki.mjs <markdownFile.md> [--title "文档标题"] [--parent <nodeToken>]
```

复用现有桥的:
- `.env` 加载(已配 `FEISHU_APP_ID`/`SECRET`)
- `@larksuiteoapi/node-sdk` 依赖(已在 package.json)
- `logger.mjs` 结构化日志
- `fetchWithRetry.mjs` 重试(图片上传、block 插入容易偶发 429)

### 方案 B:独立脚本(快速验证)

参考仓内已有的 `send-file.mjs` 模式,写一个独立 mjs 脚本先跑通最小路径:

```js
import "dotenv/config";
import lark from "@larksuiteoapi/node-sdk";
import { readFileSync } from "node:fs";
import { cleanConvertedBlocks } from "./mdToBlocks.mjs"; // 清洗:剥 style、重映射 block_id、表格去 cells

const md = readFileSync(process.argv[2], "utf8");

const client = new lark.Client({
  appId: process.env.FEISHU_APP_ID,
  appSecret: process.env.FEISHU_APP_SECRET,
  appType: lark.AppType.SelfBuild,
});

// 1. Markdown → blocks(官方 convert 接口)
const conv = await client.request({
  method: "POST",
  url: "/open-apis/docx/v1/documents/blocks/convert",
  data: { content_type: "markdown", content: md },
});
const blocks = cleanConvertedBlocks(conv.data.blocks);

// 2. 创建知识库节点(origin 会新建空文档,返回 obj_token 即 document_id)
const wiki = await client.wiki.spaceNode.create({
  path: { space_id: process.env.FEISHU_WIKI_SPACE_ID },
  data: {
    obj_type: "docx",
    parent_node_token: process.env.FEISHU_WIKI_PARENT_NODE_TOKEN || undefined,
    node_type: "origin",
    title: process.argv[3] || "未命名文档",
  },
});
const docId = wiki.data.node.obj_token;

// 3. 批量插入(单次 ≤50,超出分批;表格走 descendant 接口)
await client.docx.documentBlockChildren.create({
  path: { document_id: docId, block_id: docId },
  data: { children: blocks, index: 0 },
});

console.log("✅ 已上传:", `https://<租户>.feishu.cn/wiki/${wiki.data.node.node_token}`);
```

### 方案 C:Markdown 仓库批量同步

写一个 `scripts/sync-md-to-wiki.mjs`,遍历目录所有 `.md`,根据 front-matter 的 `title` 和 `parent` 字段做树状挂载,记录 `path → node_token` 映射到 `data/wiki-sync-index.json`,支持增量同步(已存在的按第三节第 5 步更新,不存在的创建)。

## 七、落地步骤(推荐顺序)

1. **权限审批**(浏览器,5 分钟 + 等管理员)
   - 应用详情 → 权限管理 → 开通 `docx:document` / `wiki:wiki` / `drive:drive`
   - 版本管理 → 创建新版本 → 发布
   - 建一个含机器人的群组,在知识库设置里把群组加为管理员(否则 wiki 接口 403)

2. **找 space_id**(命令行,1 分钟)
   - 用本文第二节的 curl 列出知识库,填进 `.env`

3. **跑通官方 convert 接口**(30 分钟)
   - 直接调 `blocks/convert` 转一段简单 Markdown,验证清洗逻辑(剥 style、重映射 block_id、表格去 cells)
   - 官方接口覆盖不到的语法再补自写转换器兜底

4. **跑通最小路径**(30 分钟)
   - 用方案 B 的独立脚本,上传一个简单 .md 到知识库根节点
   - 在飞书打开链接确认渲染正确、顺序无错乱

5. **补全表格和图片**(1~2 小时)
   - 表格:走 descendant 嵌套块接口
   - 图片:空 image block → upload_all(parent_node=block_id) → PATCH replace_image 三步

6. **封装 CLI + 批量同步**(1~2 小时)
   - 方案 A 入口 + 方案 C 索引文件

## 八、风险与限制

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 单文档 block 数上限 | 飞书限制约 5 万 block,长文档需分篇 | 转换器统计,超限按章节拆 |
| 嵌套列表层级 | 飞书支持但 API 构造 parent_id 树复杂 | 先支持 2 层,深层降级为扁平 |
| 图片外链失效 | 飞书不抓远程图,只认 `file_token` | 转换器下载外链图再走三步流程上传,失败则跳过 |
| 代码块语言枚举 | 飞书只认枚举值,自定义语言变 `plain` | 维护 `mdLang → feishuLang` 映射表 |
| 知识库权限 | 应用必须是知识库成员,机器人常加不进去 | 建含机器人的群组,把群组设为知识库管理员 |
| 频控 | 上传大批 block 可能触发 429 | `fetchWithRetry` 指数退避,单批 ≤50 block |
| 重复上传 | 没有去重,同名文档会重复创建 | 维护 `data/wiki-sync-index.json` 做 path→token 映射 |
| 表格合并单元格 | 飞书 API 不支持跨列合并 | Markdown 本身无此特性,直接映射即可 |
| convert 输出不稳定 | 官方转换接口有社区反馈顺序错乱、输出块需清洗 | 清洗层 + 插入后抽查;不符合预期时回退自写转换器 |

## 十、备选方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **本方案:官方 convert + 少量自写** | 完全可控,可批量,可增量同步 | 需清洗 convert 输出,图片/表格仍要手写 | 长期、批量、自动化 |
| 纯自写转换器(本方案 2026-10 前的路线) | 不依赖官方接口行为 | 工作量大,映射层要自己维护 | 官方 convert 不满足需求时 |
| 飞书"导入"功能(浏览器) | 零开发 | 必须手动、不支持 API 调用、富文本还原差 | 一次性、单文档 |
| 第三方工具 `lark-docx` | 现成转换器 | 维护停更、覆盖语法不全 | 快速验证 |
| 飞书 AI 助手生成 | 内容也由 AI 写 | 内容不可控、无法批量、无 Markdown 源 | 一次性草稿 |
| 用 `markdown-pdf` 转 PDF 再上传 | 还原度最高 | 不是可编辑的 docx,后续改要重传 | 归档类文档 |

**结论**:长期、批量、要可编辑的文档 → 本方案;一次性、不重要的 → 浏览器导入即可。

### 2026-10-23 审查(AI 辅助,对照官方文档、本仓 SDK 类型定义与公开踩坑记录)

**发现的硬伤(已修正)**:

1. 原流程"创建空文档 → 插 block → `POST /wiki/v2/spaces/{space_id}/nodes` 挂载"不可行:创建节点接口 `node_type=origin` 会**新建**空文档,不接受已有 `obj_token`;迁入已有文档需用 `move_docs_to_wiki`。已改为"先创建知识库节点(origin)→ 再往文档插 block"的顺序,省掉 folder_token 与移动步骤。
2. 图片上传 `parent_node` 原写为 document_id,实为**图片 block 的 block_id**;正确流程为三步:建空 image block → `upload_all` → PATCH `replace_image`(带 `document_revision_id=-1`)。
3. 表格不能用 children 接口创建(报 1770029),需走 `descendant` 创建嵌套块接口。
4. SDK 路径笔误:`client.docx.document.blockChildren.create` → `client.docx.documentBlockChildren.create`。

**重大补充(已修正)**:

5. 补充官方「Markdown/HTML 内容转换为文档块」接口(`POST /docx/v1/documents/blocks/convert`,2025-08 上线),转换路线改为"官方 convert 优先 + 输出清洗,自写转换器兜底";原方案未提及,原预估的 2~4 小时转换器开发可大幅压缩。
6. 任务列表 `- [ ]` 有原生 todo block(`block_type: 17`,`style.done` 表示勾选),原方案"无原生、用文本模拟"有误。
7. "应用加入知识库"从风险表提为前置准备第二节,并补充群组授权法(机器人常无法直接加入知识库,把含机器人的群组设为知识库管理员)。
